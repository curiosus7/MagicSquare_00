## 3. 인터뷰 답변 (과거 사실)

| 항목 | 내용 |
|------|------|
| **언제** | 지난 학기 수업 **마지막 실습** (한 번 수행) |
| **과제** | 4×4 격자, 합=34, 빈칸 2곳에 1~16 중 빠진 숫자 채우는 함수 작성 |
| **시작 계기** | 자동 채점이라 **제출 전 로컬에서 한 번은 통과**시키려 함 |
| **첫 번째 행동** | PDF 예시 격자를 `grid` 2차원 리스트로 옮기고, 빈칸은 `0`으로 넣어 `print(grid)` 실행 |
| **막힌 순간** | 후보 숫자가 2개여야 하는데 **4개**가 출력됨 |
| **그때 한 일** | `for n in range(1, 17): candidates.append(n)` 부분만 반복 수정. **25분** 동안 행·열 합 맞는지만 확인 |
| **깨달은 경로** | 과제 PDF 2쪽 하단 footnote 예시 답과 비교 → 격자에 **이미 쓰인 숫자를 빼지 않음**을 인지 |
| **막혔을 때 보던 것** | 터미널에 출력된 후보 숫자 리스트 `[3, 7, 11, 15]` |

### 인터뷰 로그 (3턴)

**Turn 1**

- **Q:** 가장 최근에 프로그래밍 수업에서 부분 마방진 과제를 코드로 다뤘을 때, 뭐 하려고 시작했는지랑 그렇게 하게 된 계기가 뭐였어?
- **A:** 지난 학기 수업 마지막 실습이었어. 4×4 격자에 빈칸 두 칸 있고, 1~16 중 빠진 숫자를 넣어서 행·열·대각선 합이 34가 되게 하는 함수를 짜는 과제였어. 자동 채점이라서 제출 전에 로컬에서 한 번은 통과시키려고 시작했어.

**Turn 2 (추궁)**

- **Q:** 과제 PDF 받고 나서, 코드 쪽에서 실제로 첫 번째로 한 일이 뭐였어?
- **A:** PDF에 있던 예시 격자를 `grid` 2차원 리스트로 옮겼어. 빈칸은 `0`으로 넣고, `print(grid)` 한 번 돌려서 형태가 맞는지 확인했어.

**Turn 3 (추궁)**

- **Q:** 코드가 막힌다고 느낀 그 순간, 화면에 실제로 뭐를 보고 있었어? 그리고 그걸 보기 직전까지 코드에서 반복해서 한 일이 뭐였어?
- **A:** 터미널에 찍힌 후보 숫자 리스트 `[3, 7, 11, 15]`를 보고 있었어. 빠진 숫자는 두 개뿐인데 네 개가 나와서 이상했거든. 그 직전까지는 `for n in range(1, 17): candidates.append(n)` 이 부분만 계속 손봤어. 격자에 이미 들어 있는 숫자를 빼는 조건을 안 넣었는데, 25분 동안은 행·열 합 맞는지만 확인하고 후보가 왜 네 개인지는 안 봤어. 결국 과제 PDF 2쪽 하단 footnote에 있는 예시 답이랑 비교하다가, "이미 쓰인 숫자를 안 뺐구나" 하고 알았어.

### 미확인 항목

- ECB·실패 조건 작성에 든 시간
- 최종 자동 채점 제출 여부·점수
- 후보 필터링 실수가 다른 빈칸 수·격자 크기에서도 반복되는지
- 대각선 합 검증 코드 작성 여부

## 6. Mom Test 해석 (멘토 노트)

### 검증된 것 (시뮬레이션 내)

- 문제의 핵심은 "마방진 알고리즘이 어렵다"가 아니라 **후보 생성 단계의 전제 오류**이다.
- 숫자 채우기·합 검증보다 **"어떤 숫자가 후보인지 확정하는 과정"**이 병목이다.
- **25분**, 후보 4개 vs 기대 2개라는 **측정 가능한 비용**이 있어, 문제가 행동에서 도출되었다.
- 깨달음이 **코드 디버깅이 아닌 PDF footnote 비교**에서 왔다 → 검증 루프가 잘못된 전제에 묶였음을 시사한다.

### 아직 검증되지 않은 것

- 일회성인지, 다른 과제·다른 빈칸 수에서도 반복되는지
- 손 계산 검증(별도 인터뷰)과 코드 구현 시 병목이 동일한지
- ECB·실패 조건 작성이 별도의 고통인지
- 본 시뮬레이션이 실제 사용자 행동을 대표하는지 (가상 인터뷰이므로 **실증 전**)
